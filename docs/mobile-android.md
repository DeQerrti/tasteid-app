# Android/Capacitor и мобильный мост

> Часть инструкции для ассистента; короткая главная — `CLAUDE.md` в корне репозитория.
> Читай целиком перед правками в `android/`, `mobile/src/` и любым кодом, который ходит по списку файлов/картинок на телефоне.

## Android/Capacitor: правки WebView — в MainActivity.java, не в layout XML

`android/app/src/main/res/layout/activity_main.xml` **никогда не
подключается** — `MainActivity extends BridgeActivity`, а
`BridgeActivity.onCreate()` (в самой библиотеке Capacitor) ставит
СВОЙ layout (`capacitor_bridge_layout_main`) и создаёт `WebView`
программно, ещё до того как наш код успевает что-то сделать. Правка
`activity_main.xml` (например, `android:scrollbars="none"`) в v0.6.30
не сработала именно по этой причине — файл просто никогда не
инфлейтится, две сборки подряд ушли с фиксом, который ничего не делал.

Любая настройка самого WebView (scrollbars, настройки рендеринга и
т.п.) идёт в `MainActivity.java`, **после** `super.onCreate(...)`,
через `getBridge().getWebView()` — только тогда WebView уже создан и
доступен.

## Мобильный мост (Capacitor Filesystem) — только пачками, никогда разом

На телефоне обращение к файлам идёт через нативный мост Capacitor, и
он не любит сотни одновременных запросов сразу — реально вешает
список/страницу на секунды, а не просто "чуть медленнее, чем на
компьютере". Это уже дважды приводило к настоящим зависаниям в разных
местах `mobile/src/main.js`: при первой загрузке большого списка
(решено `imgObserver`/`rootMargin`, резолвит только видимое) и при
резолве уже закэшированных путей (решено `queueCachedResolve` +
`window.__mobileForceResolveImages`, пачками по 12, а не все сразу).
Любой новый код, который проходится по большому списку картинок/файлов
на телефоне, обязан использовать этот же пачечный паттерн, а не просто
`Promise.all` по всему списку.
