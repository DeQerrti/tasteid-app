# Хранилище, картинки и синхронизация

> Часть инструкции для ассистента; короткая главная — `CLAUDE.md` в корне репозитория.
> Читай целиком перед правками в `core/api.js`, `electron/vault.js`, `mobile/src/vault.js`, `app/js/sync.js`.

## Резервные копии обложек (covers-backup/)

- Имя файла обложки присваивается один раз, при первой резервной копии
  (см. `slug` в `scheduleBackupCover`, `add.js`), и больше не меняется —
  меняется только расширение, если файл потом пересжимают. Значит,
  чтобы опознать «тот же файл» после операции над диском, нужно
  сравнивать имя БЕЗ расширения, а не путь целиком.
- Папка `covers-backup/` общая сразу на три источника: отзывы
  (`cover_backup`), «Любимое» (`image_backup`) и персонажи/тайтлы
  ВСЕХ тир-листов — встроенных «Персонажей» и любых своих коллекций
  (`cover_backup` у тайтла, `img_backup` у персонажа внутри). Любая
  массовая операция над этой папкой (поиск ничьих файлов, переименование,
  пересжатие) обязана сверяться со всеми тремя источниками разом —
  сверка только с отзывами уже дважды приводила здесь к реальным багам
  (ложные «ничьи» файлы у персонажей/любимого, а до этого те же файлы
  считались орфанами).
- Любая операция, которая меняет ИМЯ файла на диске (например,
  пересжатие с другим расширением), обязана в той же операции поправить
  ссылку на него в JSON (`reviews.json`/`favorites.json`/файлы
  тир-листов). Ровно эта проверка была пропущена в одной из прошлых
  версий («Сжать старые обложки», кнопку с тех пор убрали) и разломала
  обложки всем, кто ей воспользовался — почини по образцу
  `repairCoverReferences()` в `core/api.js`, если придётся писать
  что-то подобное снова.

## vault.listAllMedia() — только известные папки, никогда весь корень хранилища

Раньше обходила `this.root` целиком рекурсивно (см. `electron/vault.js`/
`mobile/src/vault.js`) — если рядом с папкой хранилища на диске
оказывалось что-то ещё своё (человек хранит там же архив другой
программы), оно молча попадало в резервную копию и в синхронизацию как
будто это собственные картинки TasteID. Реальный случай: целая
модовая сборка Minecraft-сервера, гигабайты картинок, улетевшая в
приватный GitHub-репозиторий синхронизации, и воскресавшая заново после
удаления, потому что для синхронизации это выглядело как «картинка,
которой тут никогда не было». Теперь обход ограничен списком папок,
куда TasteID сам когда-либо кладёт картинки: `covers`, `covers-backup`,
`title-covers`, `chars`, `favorites` и текущие свои коллекции тир-листа
из `site-settings.json`. Заводишь новую папку под картинки где-то ещё —
добавь её в этот список в обоих файлах (`electron/vault.js` и
`mobile/src/vault.js`), иначе резервная копия и синхронизация её просто
не увидят.

## Поиск «осиротевших» медиафайлов (findOrphanedCovers) — общие грабли

`findOrphanedCovers()` в `core/api.js` строит множество «на что есть
ссылка» (`refs`) обходом reviews/favorites/всех тир-листов и сверяет с
`vault.listAllMedia()`. Дважды здесь наступали на одни и те же грабли
при расширении охвата (сначала только `cover_gallery`/`image_gallery`,
потом остальные папки помимо `covers-backup/`):

- **Не только `*_backup`-поле.** У персонажей в тир-листе путь на диск
  может лежать в `img`, а не в `img_backup` — так выглядит персонаж,
  выбранный прямо из уже загруженной галереи (`selectedGalleryImg` в
  `chars-edit.js`): `img_backup` в этом случае пустой. У отзывов/
  «Любимого»/обложек тайтла эта путаница невозможна (там `cover`/`image`
  всегда либо внешняя ссылка, либо пусто, файл на диске лежит только в
  `*_backup`) — но это не значит, что так будет для любого будущего
  поля с тем же смыслом. Добавляешь новое место, откуда можно вставить
  картинку, — проверь, не может ли «выбрать из галереи» положить путь
  не в `*_backup`, а в основное поле.
- **decodeURIComponent обязателен.** Поля вроде `ch.img` собираются уже
  готовыми для `<img src>`, то есть каждый сегмент пути прогнан через
  `encodeURIComponent` (пробелы → `%20` и т.п.), а `vault.listAllMedia()`
  отдаёт настоящие, «сырые» имена файлов с диска. Без `decodeURIComponent`
  перед добавлением в `refs` любой тайтл или файл с пробелом (или другим
  не-ASCII символом) в имени всегда считался бы осиротевшим — реальный
  случай, 540 ложных срабатываний разом при расширении охвата на `chars/`.
- Список папок, которые вообще стоит проверять, теперь равен списку из
  раздела выше (`vault.listAllMedia()` уже ограничен ими) — расширять
  `findOrphanedCovers()` на новую папку отдельно не нужно, она появится
  сама, как только появится в `listAllMedia()`.

## Синхронизация: удалённый файл нельзя молча заливать заново

`syncOne()`/`syncOneByFetch()` в `app/js/sync.js` раньше видели «в
репозитории файла нет» только как «его никогда не было, надо залить» —
даже когда `state.images[path]` (память ЭТОГО устройства о прошлых
синхронизациях) помнила именно этот файл. Реальный случай: удаляешь
осиротевшую обложку на одном устройстве → её ещё не успевшая долететь
до GitHub копия (или сам файл, физически ещё лежащий на ДРУГОМ
устройстве) на следующей синхронизации читалась как «картинка, которой
тут никогда не было», и воскрешалась. Теперь: если `entry` для пути
существует, а в репозитории пути нет — значит, файл удалили в другом
месте, и локальная копия удаляется тоже, а не заливается заново
(ограничено путями, которые сервер вообще умеет стирать по одному
файлу — `isDeletableMediaPath()`/`DELETABLE_MEDIA_PATH` в `core/api.js`:
плоские `covers`/`covers-backup`/`favorites`/`title-covers`, и
вложенные `<раздел>/<тайтл>/<файл>` — портрет персонажа, `<раздел>` это
`chars` или id известного раздела тир-листа из `site-settings.json`.
Та же проверка **продублирована** в `app/js/sync.js` как
`isDeletableMediaPath()` — держать в синхроне вручную; клиентская
версия вложенную форму не сверяет со списком разделов, потому что этот
код вызывается только когда для пути уже есть `entry`, а значит его
поместил туда уже проверенный сервером `vault.listAllMedia()`). Помимо
этого — любая функция, которая инициирует удаление файла и потом сама
же (в том же запросе или в UI сразу следом) может вызвать
синхронизацию, обязана **дождаться** (`await`, не «запустить и
забыть») `deleteRemoteMedia()`/`deleteRemoteMediaFolder()` до того, как
разрешить дальнейший код — иначе синхронизация видит ещё не подчищенный
репозиторий и воскрешает то, что только что удалили здесь же.

## Удаление файла целиком — чисти и его историю версий

`vault.clearHistory(name)` стирает `.history/<name>/`, но вызывается
только там, где сам файл после удаления НИКОГДА не появится ни в одном
месте интерфейса заново (например, `deleteTierCollection()` в
`core/api.js` — раздел исчезает и из настроек, и из списка вкладок
«Истории версий», откатывать в принципе некуда). Это НЕ то же самое,
что удаление одной записи из общего файла вроде `reviews.json`/
`favorites.json` — там история сознательно остаётся, потому что сам
файл продолжает жить и вкладка «История версий» его по-прежнему
показывает (ссылка должна остаться рабочей, если человек передумает).
Путай эти два случая — один раз уже оставили `.history/tier-<id>.json/`
висеть вечно, недостижимым ни из одного места приложения, после того
как раздел удалили, а его историю - нет.

## Сжатие изображений — sharp на компьютере, canvas на телефоне

`core/api.js` — общий файл для настольной версии и телефона, но
платформы разные: на компьютере есть Node (там сжатие через `sharp` —
нативный модуль на N-API, работает под Electron без `electron-rebuild`),
на телефоне только WebView внутри Capacitor (DOM и canvas есть,
нативных модулей нет и быть не может). Поэтому сжатие — необязательная
зависимость `compressImage`, которую передаёт вызывающая сторона:
`electron/image.js` (sharp) на компьютере, свой код на canvas в
`mobile/src/main.js` на телефоне. Если добавляешь в `core/api.js` новую
операцию над картинками, которая должна работать на обеих платформах —
веди её так же, через параметр функции, а не импортируй `sharp`
напрямую в `core/api.js` (телефон его не соберёт).

`electron-builder` не умеет отдавать нативные модули (`.node`) из
`app.asar` — для `sharp` это уже учтено (`asarUnpack` в `package.json`:
`node_modules/sharp/**`, `node_modules/@img/**`). Добавишь ещё один
нативный модуль — не забудь то же самое, иначе собранное приложение
рухнет при первом же обращении к нему (а не сразу при запуске, так что
заметить это можно не сходу).
